POC closeout · for team-lead review

The issue-driven test & fix harness is ready for its next stage

Fourteen work items in, the proof of concept does the whole job it was scoped to do: take a queue of already-reported issues, write a failing regression test for each, fix it in an isolated sandbox, independently re-verify the fix, and land it as a pull request — or, on repos that explicitly opted in, squash-merge it under a canary-and-revert safety net, including resolving conflicts between parallel fixes. Two decisions from you decide what happens next.

What the harness does

The harness is TypeScript on Sandcastle, with every agent action running inside a disposable local Docker sandbox. It never discovers issues — humans report them; the harness works the queue. Its governing rule, enforced at every seam: an agent's own "done" is never evidence. Every fix is proven by re-running the reproduction test and the full suite in a fresh sandbox that the fixing agent cannot touch.

Two standing guarantees: no repo gets machine merging without an explicit onboarding opt-in (and the harness's own repository never opts in), and every regression test written for a fixed issue stays in the suite permanently — fixes can't silently regress later.

The problem this work item solved

Until September, the queue ran one issue at a time — safe, but slow: three unrelated fixes took three full sandbox cycles. The obvious fix, running fixes in parallel, has a known failure mode the PRD explicitly flagged as an open risk: two fixes that touch overlapping code will conflict when the second one merges, and a naive machine merge of that conflict is exactly the kind of unverified agent output the harness exists to distrust.

WI-13 brought that risk in scope and closed it, in three moves:

  1. A planning pass before each run. One model call ranks the issues and declares dependencies between them. Independent issues run concurrently; dependent ones wait. A bad or missing plan degrades loudly to a safe deterministic order — never a silent wrong answer.
  2. Concurrent waves with a shared-git lock. Fix work runs in parallel; the merge chain (review → merge → canary) serializes on one lock, so merges can't corrupt each other. If anything harness-level goes wrong mid-wave, every later merge is halted — no sibling merges onto a broken main.
  3. A verified merger for conflicts — the hard part. When two parallel fixes do collide, a bounded merger agent proposes a resolution, and that resolution is treated like any agent output: it counts for nothing until the full suite passes on it in a fresh sandbox. Only then is it published, reviewed, merged, and canaried. Red resolution → PR stays open, a human looks at it.

The story worth telling your lead

The conflict path's first live firing found a real defect in the harness itself: the gate verified and reviewed the conflict resolution, but never published it to GitHub before asking GitHub to merge — so GitHub refused. What happened next is the strongest evidence the design works:

No unverified code was merged. The failure was loud — an open PR and a FAILED line, not a silent skip. The run completed safely. The defect was fixed with new regression tests and re-reviewed, and the very next live run drove the same conflict through to a green end-to-end merge.

That is the harness's core promise, demonstrated on itself: machine output is never trusted, and failures surface instead of compounding.

How it was built

Fourteen work items, each through the same discipline: a grilled PRD carve-out → measurable spec → tickets → plan → test-first implementation with independent spec and quality reviews at every checkpoint → fresh verification → delivery record. Along the way the process itself caught two blocking defects in review and one live (the one above) — each fixed and re-verified before delivery. The POC is proven on local Docker. 2. Client-data confidentiality policy — confirm what may flow to the model API

your call

Constraint 3 · blocks: pointing the harness at any client repository, issue list, or log

Issue bodies and attached logs routinely contain internal paths and data values, so every client artifact is treated as sensitive by default. Until Bitcot's policy on sending a given client's data to a third-party AI API is explicitly confirmed per client, the harness runs only on our own fixtures. What's needed from you: the policy line — which clients (if any) are cleared, and what redaction, if any, must precede ingestion. The technical gate already exists and enforces whatever you decide.

What this evidence does and doesn't prove

Proven: the full loop end-to-end on local Docker with a real model — parallel scheduling, conflict resolution, machine merge under the revert net, and honest failure behavior, all with committed verbatim logs. Not yet proven: other repositories, other model providers, heavier parallelism than three concurrent lanes, or any client workload. The closeout is a POC boundary, not a production claim — which is exactly why the two decisions above are yours rather than ours.
