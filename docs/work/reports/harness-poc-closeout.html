For team-lead review · 2 minutes

Our fix-it harness works. Two choices decide what's next.

We built an assistant that takes a list of reported software problems, fixes each one, proves every fix with tests it runs itself, and hands the result to a human for approval. It has now done this end-to-end, on real runs, including the hard cases. We need two decisions from you to take it further.

What it does, in one line

Reported problem→ Test written (fails)→ Fixed in isolation→ Independently re-tested→ Delivered for approval
  • The machine never marks its own work. Every fix is re-tested in a fresh copy the fixing assistant can't touch. Its word "done" counts for nothing.
  • Every fix leaves a permanent tripwire. The test that proved the bug stays in the suite forever, so it can never quietly come back.
  • Humans stay in charge. By default, a person approves every fix with one click. Auto-landing exists only where a team explicitly asked for it — wrapped in an automatic undo-and-alert net.
  • It works in parallel, safely. Independent problems are fixed at the same time; overlapping ones are untangled by a "referee" whose combined fix must pass the same independent tests as everything else.

Proof it works — briefly

  • 261 automated tests pass on the delivered code; every feature has a recorded test-first build and review trail.
  • Real end-to-end runs, fully logged: multiple problems fixed in parallel, conflicting fixes resolved and landed, and a deliberately broken merge caught and automatically undone with the team alerted.

One story worth 30 seconds: on the very first live run of the conflict handler, the harness found a flaw in itself — it forgot to publish a resolved fix before asking GitHub to merge it. Nothing broke: the merge was refused loudly, the request stayed open for a human, the run finished safely. We fixed the flaw, and the next run drove the same conflict through to a clean, fully verified landing. The safety design worked exactly as intended — on itself.

The two decisions we need

Decision 1

May we move from local machines to cloud computing?

Approve a bounded cloud budget for testing on real, non-client repositories?

Today everything runs on one local machine — proven, but limited in how much it can handle at once. Cloud capacity unlocks realistic scale before we touch any client work.

Our recommendation: yes — a small, capped budget, same safety rules. If no: everything still works; we simply stay slower.

Decision 2

Which client materials may be processed?

Confirm the policy: which clients' code, issue lists, and error logs may be sent to the AI service?

Logs and issues often contain internal paths and real data, so today the harness only runs on our own practice projects. The technical gate is built and enforces whatever you decide — we just need the rule.

Our recommendation: name the first cleared client (or confirm "none yet"), and whether any information must be removed before processing.

What happens once you decide

Your 2 decisions→ Pilot on real repos→ First client project→ Team time saved, every week

Smaller improvements (alerts when a fix can't be solved, scheduled runs) are designed and waiting their turn — nothing technical is blocking.

Being precise about what's proven

Proven: the complete flow above, on real runs with a real AI, on our practice repository — including parallel fixes, conflicts, auto-landing with the undo net, and honest failures. Not yet proven: other repositories, other AI providers, and heavier workloads than three parallel fixes. That's exactly why the two decisions above are the right next step rather than a rollout.
