Plain-language functionality guide

The issue-driven test & fix loop

The harness is a software assistant that fixes problems people have already reported — and does it under one non-negotiable rule that shapes everything in this guide:

The one rule everything serves: machines never grade their own homework

No fix — not from the fixing assistant, not from the conflict resolver, not from anything automated — counts as done until it passes checks run in a brand-new copy of the project that the machine cannot influence. This single rule is why every feature below looks the way it does.

Every fix leaves a permanent tripwire

The test that proves the bug is real stays in the suite forever — the same bug can never quietly return.

Humans stay in charge

A person approves every fix by default; automatic landing exists only where a team explicitly asked for it.

When unsure, stop and ask

Anything ambiguous is left open for a person with a clear note. Nothing is forced through.

The problem it was built for

Reported bugs pile up faster than teams can fix them. AI assistants can draft fixes quickly — but nobody can safely trust a fix just because the AI says it works. So the expensive part was never writing the fix; it was checking it: re-testing it, reviewing it, and living with the fear that something subtle broke. And doing it one bug at a time made the pile grow faster than it shrank.

Getting problems in

Works from a list people already wrote

The harness never goes hunting for bugs on its own. It reads problems humans have already reported — GitHub issues, a requirements document, or a simple list — often with an attached error log, and treats that list as its work queue.

What it replaces: a shared backlog where AI assistance was unusable because nobody could trust the output. Deliberate limit: people decide what's worth fixing — the machine never does.

Duplicate detection

Before starting, it checks each problem against work already in flight or already finished — open requests, recently landed fixes, leftover branches — and skips anything already handled, saying so in the summary. If a fix was ever undone, the original problem goes back in the queue automatically.

What it replaces: two people fixing the same thing twice. Visible signal: every skip is named in the run summary — “skipped: already being handled.”

Spending cap

Each run fixes at most the number of problems it announced at the start, and the team can lower that number for any run.

What it prevents: runaway AI cost. Visible signal: the plan — including how many problems will be attempted — is printed before any spend happens.

Attachments and logs travel with the problem

Error logs, screenshots, and files attached to a report are carried into the working copy so the fix is based on the same evidence the reporter saw — with no assumption about format.

What it replaces: fixers guessing at symptoms from a one-line title.

Fixing problems

Prove it first, then fix it

For every problem, the harness first writes a small test that fails — demonstrating the bug is real and understood. Only then does it attempt the fix, and the fix counts only if that same test then passes.

What it prevents: “fixing” the wrong thing, or breaking something else and calling it done.

All work happens in an isolated copy

The fixing assistant works inside a disposable, containerised copy of the project — a private workshop with no access to the real shared code. When the work is done, the workshop is thrown away.

What it prevents: experiments damaging the real project; half-finished attempts leaking out.

Many fixes at once, when safe

A short planning step works out which queued problems are independent and which depend on each other. Independent ones are fixed simultaneously; dependent ones wait their turn. If the plan can't be trusted, the harness says so out loud and falls back to a safe one-at-a-time order — never a guess.

What it replaces: three unrelated fixes taking three full work cycles. Deliberate limit: when the plan is uncertain, speed is sacrificed first — never safety.

Checking the work — the load-bearing feature

The independent double-check

Once a fix looks ready, the harness builds a brand-new copy of the project, applies just the fix, and runs the problem's test plus the entire existing suite there. The assistant that wrote the fix has no way to influence this — a different room, a different examiner, the same exam.

What it prevents: plausible-looking fixes that are actually wrong — the single biggest risk of AI-assisted fixing. This is the feature the rest of the design exists to protect.

What you can observe: every run's summary states, per fix, that the independent re-test ran and passed — and nothing is ever reported fixed without it.
If it fails: the fix is reported FAILED with the reason, the problem stays open, and the next fix proceeds. No retry-without-a-record, ever.

The “fresh set of eyes” check after landing

On teams that allow auto-landing, after a fix enters the shared code the harness runs the whole suite once more against the updated project — the canary check.

What it prevents: a fix that was correct alone but clashes with something else — caught in seconds, not weeks.

What you can observe: a green (or red) canary line per landed fix in the run summary.

Delivering safely

Default: every fix becomes a review request

The normal delivery is a pull request — a proposal a human reviews and approves with one click. Nothing enters the shared code without a person saying yes.

Deliberate choice: automation prepares the work; people own the decision. This is the default even though auto-landing is faster.

Optional: auto-landing with an undo-and-alert net

A team can explicitly opt in (during setup, never later by accident) to let verified fixes land on their own. Even then, three layers wrap every landing: an automated review of the change first (unsure → back to a human), the canary check after, and — if anything is red — an automatic undo of the fix, an immediate stop to all further landings, and an alert naming the person to look.

Deliberate choice: speed without a net is reckless. The net costs a few seconds per fix and has already proven itself live on a deliberately broken merge.

When two fixes collide

A referee for overlapping fixes — that also gets graded

When two fixes prepared in parallel touch the same lines of code, a dedicated assistant proposes a combined version. That proposal gets no special trust: it must pass the full suite in a fresh copy, exactly like any other fix. Pass → it is published, reviewed, and landed with the usual net. Fail or unsure → the proposal is dropped and a human gets a clean, documented conflict.

Deliberate choice: the obvious shortcut — trusting the machine's merge — is exactly what the one rule forbids. The referee's work is graded like everyone else's.

What you can observe: the run log shows the collision, the referee's attempt, the independent re-test, and the outcome — whichever way it goes.

When things go wrong

Failures are loud, recorded, and never quietly retried away

If any step fails — a fix can't be verified, a landing is refused, even the cleanup after a check hiccups — the harness writes down exactly what happened and keeps going or stops as appropriate. It never silently re-rolls the dice and never papers over a failure.

What it prevents: the silent-failure pattern where automation “succeeds” by hiding what broke. Visible signal: every run is a checkable record — “it worked” always means it worked.

An honest summary after every run

Each run ends with a plain tally: how many problems were attempted, fixed, failed, skipped as duplicates, or not started — each with a link to the actual work (the pull request, the undo, the alert).

What it replaces: progress reports that need believing. Visible signal: the bottom line is auditable, never marketing.

What it doesn't do

A guide is only honest if it says where the edges are. Each of these is a decision, not an oversight, and each one has a reason:

  • It doesn't go looking for bugs. It works the list people already reported, and nothing else. Deciding what's worth fixing is a human judgement, and it stays one.
  • It doesn't run on a schedule. A person starts a run. Nothing runs unattended overnight.
  • It doesn't use cloud machinery. This proof runs on a local machine in disposable containers, and stays there until it has been signed off.
  • It doesn't manage secrets inside the working copy. Credentials are kept out of the isolated environment rather than handed to it and guarded.
  • It doesn't touch client material before sign-off. No client repository, issue list, or log goes near it until leadership has confirmed, for that client, that it may.
  • It doesn't land anything by itself unless a team asked it to. Auto-landing is opt-in per team, decided at setup — and this harness's own repository never uses it, whichever way the flag is set.

Protecting information

Nothing leaves without a secrets check

Every piece of text the harness sends out — to the AI service, to GitHub, into a report — is checked against the harness's own configured credentials before it leaves, and the send is blocked if one of them appears in it.

What it prevents: the harness leaking its own access keys into a prompt, a review request, or a log. Boundary: it looks for its own configured values, so it is not a general scan for credentials — a password or key sitting inside a client's error log is not caught here. Keeping material like that away from the harness is the job of the per-client clearance rule below, and reviewing it is a human decision.

Client material stays off limits until cleared

Error logs often contain internal paths and real data. No client repository, issue list, or log may be connected to the harness until the company has explicitly confirmed, for that client, that sending their material to the AI service is allowed. The block is technical, not just policy on paper.

What it prevents: confidentiality mistakes. Who decides: company leadership, per client — the harness enforces, it never grants.

Choices we made on purpose

Each of these had a faster or easier alternative. We rejected it deliberately:

  • Human approval by default. Rejected: auto-merge everywhere for speed — a wrong fix landing unreviewed costs more than review clicks. Auto-landing exists only behind an explicit per-team opt-in.
  • Re-test everything, including machine merges. Rejected: trusting the conflict resolver's combined fix — machine conflict resolution is exactly the kind of output the one rule exists for.
  • Stop and ask when unsure. Rejected: best-effort guesses with silent retries — a visible failure is recoverable; a hidden one compounds.
  • Fall back to slow-and-safe when the plan is uncertain. Rejected: running everything in parallel regardless — speed is sacrificed first, never safety.

How far the proof goes today

Established by live runs with a real AI: the complete flow described here, on our practice repository — parallel fixes, collisions resolved through the graded referee, auto-landing under the undo net, and honest failures. The next validation stage is the same flow on real (non-client) repositories, and then a first client project once the confidentiality decision is made. Not yet tested: other repositories, other AI providers, and heavier workloads than three parallel fixes. This guide describes designed and proven behaviour, not a production rollout claim.

One boundary to know. The automated checks cover each piece of the harness on its own. The assembled command-line path — the exact git and GitHub commands it runs when you start it — is proved by those live runs, not by the automated checks. So a change to that wiring is not covered until the next live run, and "the checks pass" is not evidence about it.
