Plain-language functionality guide

What the fix-it harness does, feature by feature

The harness is a software assistant that takes a list of problems people have already reported, writes a test that proves each problem is real, fixes it, double-checks its own work with a fresh copy it cannot influence, and hands the result to a human — or, where a team has explicitly allowed it, lands the fix itself under an undo-and-alert safety net. This guide explains every feature without jargon.

Four rules the harness never breaks

1

Machines never grade their own homework

No fix counts until it passes checks run in a brand-new, untouched copy of the code. The fixing assistant's word “done” is never accepted as proof.

2

Every fix leaves a permanent alarm

The test written to prove the problem was real stays in the test suite forever. If the same bug ever sneaks back, it is caught immediately.

3

Humans stay in charge

By default a person reviews and approves every fix. Automatic landing exists only where a team explicitly turned it on — and can never be switched on for them.

4

When unsure, stop and ask

Anything ambiguous — a fix it can't verify, a conflict it can't resolve, a check it can't run — is left open for a human with a clear note. Nothing is forced through.

Getting problems in

Works from a list people already wrote

The harness never goes hunting for bugs on its own. It reads problems humans have already reported — GitHub issues, a requirements document, or a simple list — often with an attached error log or screenshot, and treats that list as its work queue.

Why it matters: people decide what's worth fixing; the machine only does the fixing.

Duplicate detection

Before starting work, it checks each problem against work already in flight or already finished — open requests, recently landed fixes, leftover work branches — and skips anything already being handled, saying so in the summary. If a fix was ever undone, the original problem is automatically put back in the queue.

Why it matters: no wasted effort, and no two people (or machines) fixing the same thing twice.

Spending cap

Each run fixes at most the number of problems it announced at the start. The team can lower that number for any run; nothing is ever spent beyond the plan that was shown up front.

Why it matters: AI usage costs money — the bill is always predictable and agreed in advance.

Attachments and logs travel with the problem

Error logs, screenshots, and files attached to a report are carried into the working copy so the fixing assistant can study them — as raw material, with no assumption about their format.

Why it matters: the fix is based on the same evidence the person who reported the problem saw.

Fixing problems

Prove it first, then fix it

For every problem, the harness first writes a small test that fails — demonstrating the bug is real and understood. Only then does it attempt the fix. The fix counts only if that same test then passes.

Why it matters: this is what stops the machine from “fixing” something by accident, or by breaking something else.

All work happens in an isolated copy

The fixing assistant works inside a disposable, containerised copy of the project — a private workshop with no access to the real shared code. When the work is done, the workshop is thrown away.

Why it matters: experiments can never damage the real project, and half-finished attempts never leak out.

Many fixes at once, when safe

A short planning step looks at all queued problems and works out which are independent and which depend on each other. Independent ones are fixed simultaneously; ones that build on each other wait their turn. If the plan can't be trusted, the harness says so and falls back to a safe, orderly one-at-a-time approach — never a guess.

Why it matters: three unrelated fixes used to take three full work cycles; now they share one.

Checking the work

The independent double-check

Once a fix looks ready, the harness builds a brand-new copy of the project, applies just the fix, and runs the problem's test plus the entire existing test suite there. The assistant that wrote the fix has no way to influence this — it's a different room, a different examiner, the same exam.

Why it matters: this single rule is what makes machine fixes trustworthy. A fix is a fact, not an opinion.

The “fresh set of eyes” check after landing

On teams that allow auto-landing, after a fix goes into the shared code the harness runs the whole test suite once more against the updated project — the canary check, like the canary in the coal mine.

Why it matters: a fix that was correct alone can still clash with something else — this catches it within seconds, not weeks.

Delivering safely

Default: every fix becomes a review request

The normal delivery is a pull request — a proposal a human reviews and approves with one click. Nothing enters the shared code without a person saying yes.

Why it matters: automation prepares the work; people own the decision.

Optional: auto-landing with an undo-and-alert net

A team can explicitly opt in (during setup, never later by accident) to let verified fixes land on their own. Even then, three safety layers wrap every landing: an automated review of the change first (unsure → back to a human), the canary check after, and — if anything is red — an automatic undo of the fix, an immediate stop to all further landings, and an alert naming the person to look.

Why it matters: speed without a safety net is reckless; this is speed with a net.

When two fixes collide

A referee for overlapping fixes — that also gets graded

When two fixes being prepared in parallel touch the same lines of code, landing the second would normally end in a merge conflict that only a human can untangle. The harness instead asks a dedicated assistant to propose a combined version of both fixes. That proposal gets no special trust: it must pass the full test suite in a fresh copy, exactly like any other fix. If it passes, it is published, reviewed, and landed with the usual net. If it fails — or the referee is unsure — the proposal is dropped and a human is handed a clean, documented conflict.

Why it matters: parallel speed without creating a new trust problem — the referee's work is graded like everyone else's.

When things go wrong

Failures are loud, recorded, and never quietly retried away

If any step fails — a fix can't be verified, a landing is refused, even the cleanup after a check hiccups — the harness writes down exactly what happened, in its own words, and keeps going or stops as appropriate. It never silently re-rolls the dice and never papers over a failure.

Why it matters: you can audit every run. “It worked” always means it worked; anything else is on the record.

An honest summary after every run

Each run ends with a plain tally: how many problems were attempted, fixed, failed, skipped as duplicates, or not started — each with a link to the actual work (the pull request, the undo, the alert).

Why it matters: the bottom line is always checkable, never marketing.

Protecting information

Nothing leaves without a secrets check

Every piece of text the harness sends out — to the AI service, to GitHub, into a report — passes a screen that blocks credentials, keys, and tokens.

Why it matters: automation can't leak access it was never supposed to share.

Client material stays off limits until cleared

Error logs often contain internal paths and real data. No client repository, issue list, or log may be connected to the harness until the company has explicitly confirmed, for that client, that sending their material to the AI service is allowed. The block is technical, not just policy on paper.

Why it matters: confidentiality mistakes are prevented by the tool, not left to memory.

The rules that never bend

RuleIn plain words
Opt-in onlyAutomatic landing only where a team explicitly switched it on at setup — and never on our own repository.
Trust nothing unverifiedAny machine-produced work — fix, merge proposal, anything — counts only after independent re-checking.
Client data gatedNo client material enters the system without a confirmed policy decision for that client.
Tests are permanentEvery fix's proof-of-bug test stays in the suite forever.
Fixed budgetNo AI spend beyond what the run announced up front.
Contained experimentsAll machine work happens in isolated, throwaway copies — today on local infrastructure, no cloud spend.

Words we use

WordWhat it means here
QueueThe ordered list of reported problems the harness will work through.
Regression testA small automatic check that fails while the bug exists and passes once it's fixed — kept forever as a tripwire.
SandboxA disposable, isolated copy of the project where the assistant works without any access to the real code.
Pull requestA proposal to add a change, shown to a human for one-click review and approval.
Canary checkA full re-test of the project right after a fix lands — the early warning for anything the fix disturbed.
RevertAutomatically taking a landed fix back out, returning the shared code to its last known-good state.
RunOne session of the harness working through its queue, ending with an honest summary.
